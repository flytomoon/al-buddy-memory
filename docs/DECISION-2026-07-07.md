# Decision Record: Memory Architecture — Local-First SQLite, Portable by Schema

**Date:** 2026-07-07
**Status:** Accepted
**Owner:** CTO
**Related:** [Core Memory Schema](./SPEC.md) · [GOV-DAT-001](./policies/data-stewardship.md) · [GOV-TECH-001](./policies/technical-governance-and-schema-evolution.md)

## Context

Al Buddy's north star is a **lifelong AI companion with portable, model-agnostic memory** that can eventually live anywhere — laptop, cloud, or a robot. Before committing to the persistence layer, we asked whether SQLite + a graph schema is the right long-term bet, or whether we should adopt an established memory framework or match what OpenClaw / Hermes do.

We researched the current (mid-2026) landscape to answer this deliberately rather than by default.

## What the research found

- **The systems we admire converge on our pattern.** OpenClaw uses SQLite + markdown files, local-first. Nous Research's **Hermes agent uses SQLite + FTS5** with memory under `~/.hermes/`. Our in-progress `SqliteMemoryStore` (SQLite + FTS5) already matches best current practice.
- **Frameworks are engines with opinions, not portability guarantees.** The open-source memory frameworks we evaluated are all Apache-2.0 and capable, but adopting one couples us to _their_ extraction/scoring/decay semantics — the part that is hardest to carry forward later. We want to own that.
- **Portability lives in the schema + raw text, not the storage engine.** SQLite is the most portable database there is (one file, dumps to plain SQL, no server). The only real lock-in risk is **embeddings tied to a specific model**.
- **The de-facto interchange vocabulary is entities / relations / observations** (the MCP knowledge-graph memory server). Modeling our graph so it projects cleanly onto that shape keeps a cheap export path open. Existing agent-file and memory-interchange formats are worth mining for ideas but not worth depending on.

## Decision

1. **Keep SQLite as the canonical local-first store.** Single-user memory fits comfortably in one file. No server until multi-device sync is a real requirement — and that is "sync the file / replicate the store," not an architecture change. This directly serves the "run anywhere, including a robot" goal: the store is a portable artifact, the body is a peripheral.
2. **Do not adopt an external memory framework as a dependency.** We own the data model and the memory semantics.
3. **Portability is a property we engineer and prove**, via three concrete measures adopted in schema **1.1.0**:
   - **Raw text is the source of truth.** Graph edges and embeddings are derived and rebuildable.
   - **Bi-temporal validity** (`validFrom` / `validTo`, `validAt` queries): superseded facts are invalidated, not deleted, so the memory records how a life changes over time.
   - **Embeddings as a model-tagged, disposable cache** in a dedicated side store, so upgrading the embedding model is a re-index, never a data-loss migration.
4. **Ship an exporter** to the MCP entities/relations/observations JSON shape as portability insurance. _(Follow-up — not in the 1.1.0 change; tracked below.)_

## Consequences

- Schema bumped 1.0.0 → **1.1.0** (see the schema doc changelog). Changes are additive/back-compatible: `validFrom` defaults to creation time, `validTo` to `null`; inline `MemoryNode.embedding` is deprecated in favor of `setEmbedding`/`getEmbeddings`.
- `SqliteMemoryStore` now self-migrates via `PRAGMA user_version` (migration `v2`), so existing databases upgrade on open.
- We take on ownership of memory extraction/consolidation logic rather than inheriting it from a framework — deliberate, and the source of our differentiation.
